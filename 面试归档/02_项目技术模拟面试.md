## 两个项目的事实卡

### FlowChain：可确认的内容

- 平台把文档解析、OCR、大模型、文本处理等原子能力封装为节点，支持画布编排和模板复用。
- 用户简历写明从零搭建租户端工作流模块，负责画布到后端引擎的 DAG 数据解析、业务逻辑校验和结构适配。
- 负责编辑、发布相关接口；简历结果为百级节点流程发布响应 500ms 内、TPS≥30、成功率 99.9%。
- 接入 SkyWalking、自定义业务 Span 及微服务链路上下文传递，简历结果为平均定位时间从 30 分钟缩短至 5 分钟。
- 已知优化描述仅为梳理业务流程和调整代码逻辑结构，没有提供具体代码、原始执行计划或压测记录。

不能据此确认使用过拓扑排序、批量数据库写入、缓存节点元数据、并行校验、发布版本快照或只遍历一次。它们可以作为设计讨论，不能替代实际经历。

### UniAIGC：可确认的内容

- 逻辑架构分租户面、运行面和系统面，使用 Spring WebFlux、Netty。
- 配置热同步采用 Redis 发布订阅、本地缓存、接口定时拉取兜底。
- 流控基于 Redis，支持分钟和日粒度。
- 权限有系统平台通用级和租户级，租户可配置权限，通过权限表及租户查询范围隔离。
- 责任链顺序为权限、限流、Prompt 安全校验 API、模型网关。
- 模型名称映射 Spring Bean 管理的 ModelClient，不同 Client 适配不同模型协议。
- 历史统计由实时明细查询改为独立统计表查询，相关接口耗时控制在 3 秒内。

三面隔离的具体部署边界、热同步消息是否带版本、权限撤销延迟、Redis 不可用时策略、计数维度和限流原子实现仍需补齐。

## 每组追问的准备方法

### 流控：把计数规则说明白

至少确认以下信息后再形成完整项目答案：

| 需要确认 | 为什么会被追问 |
| --- | --- |
| 限流对象：系统、租户、模型或组合维度 | 决定计数器与策略如何对应 |
| 分钟、日窗口是固定还是滑动 | 决定窗口边界及短时流量特征 |
| 额度来源和更新方式 | 决定运行中配置变化如何生效 |
| 检查与递增的实际实现 | 独立 GET、判断、INCR 不能自然组成原子业务操作 |
| 两个窗口怎样同时通过 | 避免分钟已占用而日额度拒绝等计数口径混乱 |
| 失败、取消和重试是否计数 | 决定“准确”是请求次数、放行次数还是成功次数 |
| 超时后客户端是否知道计数成功 | 决定能否直接重试及是否需要幂等 |
| Redis 故障和集群 Key 约束 | 决定可用性及多 Key 操作是否能落地 |

Lua 是可能的原子实现方案，但本次没有确认该模块实际采用 Lua。即使采用，Lua 中途执行错误也不会自动回滚先前成功的写入。排队组件使用 Redis＋Lua，不等于限流模块也使用相同方案。

### 权限与配置同步：说明边界

准备系统权限与租户权限如何组合、租户标识如何确认、权限表查询如何限定范围。对“可信请求上下文中的租户身份”属于合理设计建议，未提供实际鉴权代码之前不能说成已核实的实现。

Redis 发布订阅不提供离线消息补发；定时拉取有助于修复漏通知，但不能直接保证强一致。准备初始加载、更新顺序、版本控制、缓存替换、刷新失败和权限撤销的行为。

### 发布性能：补齐证据

发布 API 耗时与工作流执行耗时是不同指标。现在已能说明发布链路涉及解析、校验、转换及持久化，还需要补四项：

1. 原来最慢的是哪个阶段，有没有调用链、日志或压测证据？
2. 修改了哪段逻辑，怎样减少查询、遍历、转换或等待？
3. 百级节点的节点类型、连线数量、并发及环境是什么？
4. 优化前后是否用相同输入比较，校验正确性是否保留？

原始指标没有确认平均值、P95/P99、样本时间或机器配置，不自行补全。找不到实际改动证据时，可用统计表改造讲性能案例，FlowChain 侧重模块设计与交付。

## 代码设计题的修正参考

以下属于“如果现在设计”的方案，不是原项目实录。

1. 发布应用服务编排解析、通用校验、节点专属校验、转换和持久化，统一输出校验结果。
2. 每种节点实现专属校验策略，由注册表按类型选择；通用规则复用公共校验器。
3. 多条独立校验规则可用校验器列表或责任链组织，明确失败后停止还是汇总错误。
4. 使用节点集合、边集合及邻接关系表达 DAG。组合模式通常面向树形层级，DAG 可能共享节点、多父节点，不应直接宣称“用组合模式表示 DAG”。
5. 若需要验证 DAG 无环，可评估拓扑排序；这是设计选择，不能追认为已实现。
6. 将“减少重复解析、按类型避免无效校验、批量读取配置”等作为待测优化点。策略模式改善扩展性，本身不证明性能变快。
